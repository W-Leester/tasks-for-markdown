## 1. 미리보기 플러그인이 전혀 동작하지 않음 (09-21, 8b8b639)
- **증상:** 마크다운 미리보기에 태스크 표시와 ```tasks 결과가 안 나옴. 다른 기능은 정상.
- **원인:** `package.json`에 `contributes.markdown.markdownItPlugins`처럼 **중첩 객체**로 적음. VS Code는 `"markdown.markdownItPlugins": true` 같은 **평평한 점 표기 키**만 인식하고, 중첩 객체는 조용히 무시한다.
- **해결:** 키를 평평하게 고침. 키 형태를 확인하는 회귀 테스트, 미리보기 엔진 적용 통합 테스트 추가.
- **재발 방지:** 기여점은 공식 문서의 키 표기를 그대로 쓴다. "아무 일도 안 일어남"은 등록 실패를 먼저 의심.

## 2. 만들기/편집 단축키가 다른 기능과 충돌 (09-21~22, 6656b0b → e264464)
- **증상:** `Cmd+Alt+T`를 누르면 열린 에디터들이 닫힘 → 바꾼 `Ctrl+T`는 macOS 에디터에서 안 먹힘 → 최종 `Ctrl+Shift+C`도 처음엔 에디터 안에서 동작 안 함.
- **원인:** `Cmd+Alt+T`는 VS Code의 "Close Other Editors". macOS `Ctrl+T`는 텍스트 시스템의 글자 교환(transpose). when 절의 `!inputFocus`는 **텍스트 에디터 안에서도 true**라 에디터에서 꺼짐.
- **해결:** `Ctrl+Shift+C`, when 절 `!terminalFocus && (editorTextFocus || !inputFocus)`.
- **재발 방지:** 키를 고를 때 VS Code·Cursor 기본 키, macOS 텍스트 시스템 키, 인기 확장 키를 모두 확인(14번 참고).

## 3. 자정 이후 통합 테스트 실패 (09-22)
- **증상:** 한국 시간 자정~오전 9시에만 날짜 관련 테스트 실패.
- **원인:** 기대값을 `toISOString()`(UTC)로 만듦 → "오늘"이 하루 어긋남.
- **해결:** `localToday()` 도우미로 로컬 날짜 비교.
- **재발 방지:** 날짜 테스트는 로컬 날짜 기준. 시간대에 따라 결과가 바뀌는지 의심.

## 4. Markdown All in One과 함께 쓰면 미리보기가 빔 (09-22, 65d8f63 → 되돌림 → 재적용 938d509)
- **증상:** 태스크가 있는 파일만 미리보기가 빈 화면.
- **원인:** 다른 확장(markdown-it-task-lists)이 먼저 `[ ]`를 지우고 체크박스를 넣음 → 우리 플러그인이 예외 → 렌더링 전체 중단.
- **해결:** 우리 렌더러 전체를 try/catch로 격리(실패해도 미리보기를 비우지 않음), 다른 확장이 넣은 체크박스에서 상태를 복구.
- **재발 방지:** 공유 파이프라인(미리보기 렌더러)에 끼어드는 코드는 **절대 예외를 밖으로 내보내지 않는다.** 인기 확장과 함께 건 테스트를 둔다.
- **과정의 교훈:** 검증 중 Cursor GUI를 자동으로 띄워 로그인 창이 사용자를 방해했고, 다른 증상과 섞여 수정을 통째로 되돌렸다가 다시 적용했다. → Cursor GUI는 자동으로 띄우지 않는다.

## 5. 대화상자 적용 버튼 무반응 (09-22, beae3a1)
- **증상:** 편집 대화상자에서 적용을 눌러도 아무 일 없음.
- **원인:** Svelte 5의 상태 객체(프록시)를 그대로 `postMessage`에 넘김 → 웹뷰가 메시지를 복제하지 못해 `DataCloneError`.
- **해결:** 보내기 전에 `$state.snapshot`으로 일반 객체로 바꿈.
- **재발 방지:** 웹뷰 테스트의 가짜 `postMessage`도 실제처럼 `structuredClone`을 하게 함(그래야 이런 회귀를 잡음).

## 6. 기본 미리보기가 빈 화면 (09-29, a03c748)
- **증상:** 예시 노트를 VS Code 미리보기로 열면 아무것도 안 보임.
- **원인:** 첫 줄 `---`는 있는데 **닫는 `---`가 없어** 문서 전체가 front matter로 처리됨. Cursor의 WYSIWYG 편집기로 고치다 닫는 줄이 사라졌고, 디스크에서 고쳐도 Cursor 편집기가 다시 덮어씀.
- **해결:** 에디터 진단(경고)과 빠른 수정(맨 위 `---` 삭제) 추가.
- **재발 방지:** 사용자 파일 내용 때문에 생기는 문제는 진단으로 알려 준다. 편집기에 열린 파일은 디스크에서 고치지 않는다.

## 7. 렌더 보기에서 줄 버튼이 안 보임 (1.7.0~1.8.0 → 09-29 88ce43d)
- **증상:** 태스크 줄에 마우스를 올려도 `✎ ⏩ 💬` 버튼이 안 나옴. 메모 기능 테스트 중 발견.
- **원인:** 열 배치(1.7.0)에서 버튼을 설명 칸 **안으로** 옮겼는데, 보이게 하는 CSS는 `li:hover > .rv-actions`(**바로 아래 자식만**)라 매칭이 안 됨.
- **해결:** 줄·`<p>`·설명 칸 안의 버튼 모두에 맞는 선택자.
- **재발 방지:** "버튼이 만들어지는지"가 아니라 **"실제로 보이는지"**(계산된 스타일) 테스트. DOM 구조를 바꾸면 그 구조를 가리키는 CSS도 확인.

## 8. 열 제목이 열과 어긋남 (09-30, M15 개발 중)
- **증상:** 쿼리 결과 위 열 제목이 실제 열보다 약 100px 오른쪽에 그려짐. 스크린샷 점검에서 발견(배포 전).
- **원인:** 열 폭이 `em` 단위인데, 제목 줄에 작은 글자 크기를 주어 `em`이 줄어듦.
- **해결:** 제목 줄은 행과 같은 글자 크기, 글씨만 작게.
- **재발 방지:** 화면 변경은 headless Chrome 스크린샷으로 눈으로 확인. 애니메이션은 끄고 캡처.

## 9. Cursor에서 `Cmd+K` 단축키 안내가 안 맞음 (09-30, 3bad355)
- **증상:** 수동 점검 문서의 `Cmd+K` → `Cmd+T`(색 테마)를 누르면 AI 입력 상자가 뜸.
- **원인:** Cursor는 `Cmd+K`를 AI 인라인 편집에 씀 → `Cmd+K`로 시작하는 두 단계 단축키가 동작하지 않음(`Cmd+K V`도).
- **해결:** 문서를 명령 팔레트 기준으로 고침.
- **재발 방지:** 문서의 단축키 안내는 명령 팔레트 명령 이름을 함께 적는다. Cursor 예약 키: `Cmd+K`, `Cmd+L`, `Cmd+I`, `Cmd+Shift+V`.

## 10. 영어 화면에 한국어 명령 이름 (09-30, 3bad355)
- **증상:** 기본(영어) 번역 파일 137개 중 51개가 "한국어 (English)" 형태 → 영어 화면 사용자에게 한국어가 보임.
- **원인:** 예전에 사용자의 영어 화면 Cursor에서 한국어를 보이게 하려고 기본 파일에 한국어를 섞음.
- **해결:** 기본 파일은 영어만, 한국어는 `package.nls.ko.json`. 기본 파일에 한글이 있으면 실패하는 테스트.
- **재발 방지:** 화면 언어별 표시는 번역 파일로만 해결한다.

## 11. 설치 파일에 예시 노트·압축 파일이 들어감 (09-30 dfaa184, 10-01 c0e8d5f)
- **증상:** `examples/`(편집 중이던 개인 노트 포함)가 설치 파일에 들어감. 다른 날엔 크기가 600KB → 1.17MB로 늘었는데, 프로젝트 폴더에 남아 있던 `.vsix.zip`이 통째로 들어간 것.
- **원인:** `.vscodeignore`가 "빼는 목록" 방식이라 새로 생긴 파일이 자동으로 포함됨.
- **해결:** `examples/**`, `*.zip`, 원본 아이콘 제외.
- **재발 방지:** 포장할 때마다 파일 수와 크기를 본다(가이드라인 2.3).

## 12. 배포 워크플로가 게시를 항상 건너뛸 뻔함 (09-30, dfaa184에서 수정)
- **증상:** (배포 전 점검에서 발견) 토큰을 등록해도 Marketplace·Open VSX 게시 단계가 실행되지 않았을 것.
- **원인:** 게시 단계에 `env: VSCE_PAT: ${{ secrets.VSCE_PAT }}`와 `if: env.VSCE_PAT != ''`를 함께 씀. **같은 단계의 `env`는 그 단계의 `if`에서 보이지 않는다.**
- **해결:** 토큰을 job 수준 `env`로 옮김.
- **재발 방지:** 조건부 단계는 실제로 한 번 돌려 보거나, 조건 값을 로그로 확인.

## 13. 새 패키지 추가 후 CI 설치 실패 (09-30, dfaa184)
- **증상:** (배포 전 발견) `pnpm install --frozen-lockfile`이 "lockfile에 `packages/api`가 없다"며 실패.
- **원인:** 의존성이 하나도 없는 워크스페이스 패키지는 pnpm 12가 lockfile에 넣지 않으면서, frozen 설치에서는 요구함.
- **해결:** 빌드에 실제로 쓰는 `typescript`를 개발 의존성으로 명시 → lockfile에 들어감.
- **재발 방지:** 워크스페이스 구성을 바꾸면 로컬에서 `--frozen-lockfile` 설치를 한 번 돌린다.

## 14. `Cmd+Enter` 완료 토글이 Cursor에서 안 됨 (10-01, c0e8d5f → 4d87ae4 → 76c745b)
- **증상:** 태스크 줄에서 `Cmd+Enter`를 누르면 완료 대신 아래에 체크박스 줄이 생김. Cursor에서는 처음부터 동작하지 않았음.
- **원인:** Markdown All in One도 마크다운에서 `Cmd+Enter`를 씀. Cursor는 그쪽을 선택.
- **잘못 간 길:** 우선순위 규칙을 코드로 분석해 "우리 쪽이 먼저 검사된다"고 결론 내리고, 키를 넘겨주는 명령(`tasksmd.enterKey`)을 만들었지만 실제로는 여전히 짐 → 되돌림. 이후 `Cmd+Alt+X` → 사용자 의견으로 `Ctrl+Shift+Enter`.
- **해결:** 기본 키 `Ctrl+Shift+Enter`(macOS도 Ctrl, `Ctrl+Shift+C/R`과 같은 계열). Cursor·VS Code 기본 키, Markdown All in One, 설치된 확장 어디에도 쓰이지 않음을 확인.

## 19. 실패를 숨기거나 파일을 망가뜨린 작업 방식 (상시)
- **파이프가 실패를 숨김:** `pnpm test | grep …`의 종료 코드는 grep의 것이라, 실패한 채 커밋된 적이 있다 → `set -o pipefail`/`PIPESTATUS` 확인, 또는 결과 줄(`Tests … passed`)을 직접 본다.
- **치환 스크립트가 파일을 비움:** 대상 문자열이 없을 때 빈 조각으로 덮어 파일을 비운 적이 있다 → 치환 전 `assert 대상 in 내용`, 사고 시 `git checkout`으로 복구.
- **JSDoc 주석 안의 `*/`:** 주석에 `**/`나 `/* */`를 쓰면 주석이 거기서 끝나 TypeScript가 깨짐 → 주석의 예시 경로를 바꿔 씀.
- **CLI가 `| head`에서 EPIPE로 죽음:** 출력 파이프가 먼저 닫혀서 생긴 오류 → EPIPE는 정상 종료로 처리.
- **위험한 삭제 명령:** `rm -rf $변수/…`는 변수가 비면 엉뚱한 곳을 지울 수 있어 안전 장치에 막혔다 → 절대 경로나 `"${VAR:?}"`를 쓴다.
- **원격 점검 혼선:** SSH 사용자 이름 오타(`lesster`), 저장 안 된 편집기 때문에 바깥 수정이 안 보임 → 오류 로그의 실제 값(사용자 이름 등)을 먼저 확인. 바깥 수정 시험은 편집기에 열지 않은 파일로.

## 23. 브라우저 VS Code에서 칸반·캘린더 편집 후 "Could not edit" 오류 (10-03, 브라우저 전용으로 확인)
- **증상:** README용 GIF를 `code serve-web`(브라우저에서 도는 VS Code 1.140)으로 찍는 중, 칸반에서 카드를 옮기거나 캘린더에서 날짜를 옮기면 **파일은 바르게 바뀌는데** "Tasks: Could not edit …/work.md" 오류 알림이 뜬다. 확장 로그에도 `webview kanban: Could not edit`이 매번 남음. 렌더 보기의 체크·메모 추가는 같은 환경에서 오류 없음.
- **파악한 것:** 오류는 `TaskEditService`에서 `workspace.applyEdit`가 `false`를 돌려줄 때 난다. 서버를 새로 띄우고, `work.md`를 편집기에 열지 않아도 재현. 데스크톱 Cursor 수동 점검(칸반·캘린더)에서는 보고된 적 없음.
- **조치:** GIF에서는 알림 영역만 감춰 촬영(편집 결과는 실제 파일 변경으로 확인). 원인은 아직 모름 — 데스크톱 VS Code에서 같은 동작을 재현해 보고, 재현되면 고친다.
- **확인(10-04):** 데스크톱 VS Code 통합 테스트에서 칸반 카드 옮기기(상태·마감일 변경)와 캘린더 날짜 옮기기와 같은 메시지를 보내고, 파일 내용과 함께 **웹뷰로 오류 메시지가 나가지 않았는지**를 단언하도록 고침(`recordSent`). 52개 모두 통과 — 데스크톱에서는 `applyEdit`가 정상으로 성공을 돌려준다. 따라서 `code serve-web`(브라우저 VS Code) 환경의 동작으로 보고 코드는 그대로 둔다.
- **재발 방지:** 웹뷰 편집 테스트는 결과 파일뿐 아니라 오류 보고가 없는지도 확인한다. 브라우저 VS Code(vscode.dev 등)를 정식 지원하게 되면 다시 조사.

## 26. 한국어 설정에서도 웹뷰 첫 화면 일부가 영어 (10-03)

- **재발 방지:** 웹뷰 컴포넌트 테스트에 "메시지 전 첫 화면이 번역됐는지"를 둔다. 번역처럼 화면 전체에 쓰이는 값은 메시지가 아니라 페이지와 함께 보낸다.

## 28. 시작 안내 버튼이 "마크다운 파일을 여세요"로 실패 (10-07)

## 29. Cursor에서 시작 안내를 열 방법이 없었음 (10-07)

## 34. 렌더 보기 열 경계를 끌면 앞의 경계가 모두 함께 움직임 (10-10, 1.0.0~1.1.0)
- **증상:** 열 제목 줄에서 생성일이나 나머지 필드의 경계를 끌면 잡은 선만이 아니라 설명 열과의 사이에 있는 모든 경계가 같이 밀림(사용자 보고).
- **원인:** 손잡이(열의 왼쪽 경계)가 **그 열 너비만** 바꾸고 남는 폭은 설명 열(1fr)이 흡수. 표는 오른쪽 끝에 붙어 있어, 사이에 낀 고정 폭 열들이 통째로 이동했다. M16 계획에는 "다른 경계는 움직이지 않는다"고 적었지만 구현과 테스트는 첫 번째 열(설명 옆)만 다뤄 어긋남을 못 봤다.
- **해결(M24):** 순수 함수 `moveBoundary` — 왼쪽 이웃이 다른 열이면 두 열이 너비를 주고받음(합 유지, 둘 다 3~40em 안에서 멈춤), 설명 옆이면 그 열만. 키보드도 같은 규칙. 테스트에 "가운데 경계" 경우 추가.
- **재발 방지:** 계획의 문장("다른 경계는 그대로")을 테스트로 옮긴다 — 끝 열뿐 아니라 **가운데** 경우까지. 끌기 UI는 실제로 끌어 본다.
- **고친 뒤 사용자 점검에서 다시 실패(10-11):** (a) **더블클릭이 VS Code·Cursor 모두 아무 일도 안 함** — 손을 뗄 때 제목 줄을 다시 그려(`innerHTML`) 두 번째 클릭은 새 요소 위에서 일어나 dblclick이 오지 않았다. jsdom 테스트는 dblclick 이벤트를 직접 보내 이걸 못 잡았다. (b) **될 때와 안 될 때가 있음, Cursor와 VS Code가 다름** — 좁은 창에서 설명 열이 최소(8em)라 설명 옆 열을 넓히면 오른쪽 열이 통째로 밀렸고, "나머지 필드"는 설정보다 좁게 그려져 계산이 화면과 어긋났다. Cursor 패널이 더 좁아 두드러졌다. (c) 마지막 손잡이를 왼쪽으로 끌면 이웃이 3em에서 멈춤.
- **두 번째 해결:** 손을 뗄 때 aria 값만 갱신(요소 유지), 시작 너비를 그려진 폭으로 재고 설명 열은 남는 폭만 내주게(`descRoom`), 왼쪽으로 끌 때 다음 열들이 차례로 내주는 밀기. **실제 Chrome(헤드리스, puppeteer)에서 렌더 보기 CSS·스크립트 그대로 띄운 시험 페이지로 1000px·700px 창에서 끌기·더블클릭을 돌려** 고치기 전 실패와 고친 뒤 동작을 확인.
- **세 번째(10-11):** 마감일이 최대 40em에 닿은 상태에서 그 손잡이를 더 끌 수 없음(사용자 캡처). 그 열만 넓히다 최대에 닿으면 멈췄다. → 경계 오른쪽 열들도 차례로 받게, 최대 80em(마지막 열은 받아 줄 열이 없음). 같은 상태(2000px, 마감일 40em)를 시험 페이지에서 재현해 확인. **교훈 추가:** 한도(최소·최대)마다 "닿았을 때 계속 끌면?"을 테스트에 넣는다.
- **교훈:** jsdom에는 레이아웃이 없다 — 끌기·더블클릭·폭 계산은 실제 브라우저에서, **좁은 창 포함**해 확인한다. 이벤트를 직접 보내는 테스트는 "브라우저가 그 이벤트를 보내는가"를 검증하지 못한다.

## 36. Windows에서 Claude Code 연결 실패, PATH 안내가 macOS 문구 (10-14, 1.1.0~1.1.1)
- **증상(사용자 Windows 점검):** 첫 실행 알림의 연결 → "제대로 설치가 안 됐다", `claude mcp list`는 "No MCP servers configured". `tasksmd` 설치 알림은 "셸 설정 파일(~/.zshrc)에 넣으세요: `setx PATH "%PATH%;…"`".
- **원인:** (1) 외부 명령을 Windows에서 `execFile(..., { shell: true })`로 실행 — Node는 셸 모드에서 인자를 이스케이프 없이 cmd.exe 명령줄로 이어 붙인다. `claude mcp add-json`의 JSON(따옴표, 공백 든 `…\Microsoft VS Code\Code.exe`)이 깨졌다. npm으로 깐 `claude`는 `claude.cmd`라 셸 없이는 Node가 실행을 거부해서 셸을 켰던 것. `tasklist` 인자도 셸 기준으로 따옴표를 붙여 두었다. (2) PATH 안내 문장이 플랫폼 구분 없이 macOS 기준이었고, Windows 줄은 `setx`(1024자 절단, 시스템 Path를 사용자 Path로 복사).
- **왜 못 잡았나:** Windows 코드는 순수 함수(런처 내용·경로) 단위 테스트만 있었고, 프로세스 실행과 화면 문구는 Windows에서 돌려 본 적이 없다("확인 전까지 알려진 한계"로 둔 상태로 1.1.0 배포).
- **해결(1.1.2):** cmd.exe를 거치지 않는다 — PATH에서 `.exe`를 찾으면 바로, npm `.cmd` 심(shim)이면 심이 실행할 스크립트(`…\cli.js`)를 읽어 에디터 Node로(`src/ai/winCommand.ts`, 파일 접근을 주입해 가짜 Windows 파일 시스템으로 테스트). 복사용 명령은 JSON 없는 `claude mcp add … -e ELECTRON_RUN_AS_NODE=1 -- …`. PATH 안내는 Windows 전용 문장 + 사용자 Path만 바꾸는 PowerShell 한 줄.
- **두 번째(같은 날 재점검):** 고친 뒤 "연결했습니다"가 나왔는데 `claude mcp list`가 여전히 비어 있음. VS Code의 Windows `fsPath`는 드라이브 문자가 **소문자**(`c:\\…`)라 Claude Code가 `projects["c:/…"]`에 저장했고, 터미널(`C:\\…`)에서는 다른 폴더였다. 사용자 `~/.claude.json`에 대소문자만 다른 키가 실제로 있어 PowerShell `ConvertFrom-Json`이 "중복된 키"로 거부한 것이 단서. 또 우리 "이미 연결됨" 확인은 백슬래시 경로로 찾아 슬래시 키(`C:/…`)와 늘 어긋났다. → `folderPathFor`(Windows 드라이브 문자 대문자)로 작업 폴더·`--root`를 넘기고, 확인은 슬래시만 맞춰 비교. **세 번째:** 처음엔 확인을 대소문자 무시로 해서, 남아 있던 옛 `c:/…` 항목을 "이미 연결됨"으로 보고 추가를 건너뜀 → Claude Code처럼 **대소문자 구분**으로 바꿈. **교훈 추가:** 다른 도구가 경로를 키로 쓰면 그 도구가 저장하는 **정확한 모양**(구분자·대소문자)과 **비교 방식**을 그대로 따른다 — 우리 쪽에서 더 너그럽게 비교하면 그 도구가 못 찾는 항목을 "있음"으로 본다.
- **네 번째(10-15, 실제 Windows PC에서 1.1.1 점검):** 런처 `tasksmd.cmd`와 MCP 서버 본체(stdio로 initialize·tools/list·tasks_query)는 Windows에서 정상 — 고장난 건 등록 단계와 안내문뿐임을 확인. 그런데 1.1.2의 복사용 명령 `claude mcp add … -- …`를 PowerShell에 붙여 넣으니 "unknown option '--root'". 셸 자체는 맨 `--`를 통과시키지만(`node -e` 로 확인), PowerShell은 `claude`를 npm의 **`claude.ps1` 심**으로 먼저 잡고, 그 스크립트가 `$args`로 인자를 넘기면서 PowerShell이 맨 `--`(매개변수 끝 표시)를 `$args`에서 **빼 버린다**. `claude.cmd …`·cmd.exe는 정상. → 복사용 명령의 `--`를 `"--"`로 — PowerShell은 따옴표 친 `--`를 보통 인자로 두고, cmd.exe/Node의 인자 파싱은 따옴표를 벗겨 `--`를 넘기므로 두 셸 모두 통과(둘 다 실제로 실행해 확인). 확장 내부 경로(add-json을 Node로 직접 실행)는 `--`를 안 쓰므로 무관.
- **재발 방지:** Windows에서 외부 명령을 실행할 때 `shell: true`를 쓰지 않는다(인자가 이스케이프되지 않음). 플랫폼별 문구는 플랫폼마다 따로 쓴다. "Windows 미확인" 상태의 기능은 배포 후 가장 먼저 실제 Windows에서 점검한다. 사용자가 붙여 넣을 명령은 **Windows PowerShell 5.1에서 npm 설치판으로** 실제로 붙여 넣어 본다 — npm 심은 `.ps1`이 먼저 잡히고, `$args`를 거치는 순간 맨 `--` 같은 PowerShell 토큰이 사라진다.

## 37. Release 워크플로가 통합 테스트에서 두 번 연속 멈춰 실패 (10-15, 1.1.3)
- **증상:** 태그 `v1.1.3` 푸시 → Release 실패. 로그 끝: `CodeWindow: detected unresponsive`, Exit code 1. Open VSX·npm 게시 단계는 돌지 않음.
- **원인:** 헤드리스 VS Code(runner의 1.142.0)가 시작 중 멈추는 알려진 불안정(배포 가이드에 기록, 1회 재시도 있음). 이번엔 재시도까지 두 번 모두 멈춤. 코드 문제 아님(로컬 61 passing, 재실행 61 passing).
- **해결:** `gh run rerun --failed` → 통과·게시 성공. 게시 전 단계라 중복 게시 위험 없음.
- **재발 방지:** 가이드에 재실행 절차 추가. 자주 반복되면 재시도 2회 또는 runner의 VS Code 버전 고정 검토.

## 38. 편집 창의 날짜 선택 아이콘이 잘려 보임 (10-15, 1.0.0~1.1.3, 다크 테마)
- **증상(사용자 캡처):** `Ctrl+Shift+C` 대화상자의 마감일 칸 오른쪽 달력 아이콘이 조각만 보임.
- **원인:** 날짜 선택을 `<input type="date">` 하나로 두고 폭을 1.6em으로 줄였다. Chromium은 그 안에 "mm/dd/yyyy" 글자와 아이콘을 모두 그리므로 아이콘이 잘렸고, `color-scheme`을 지정하지 않아 다크 테마에서는 아이콘이 어둡게 그려졌다. 라이트 테마·넓은 창에서만 보고 넘어감.
- **해결(1.1.4):** 글자 부분(`::-webkit-datetime-edit`)을 숨기고 아이콘(`::-webkit-calendar-picker-indicator`)이 2em 상자를 채우게, `body.vscode-dark`·고대비에서는 `color-scheme: dark`. `showPicker()`는 쓰지 않음(웹뷰는 다른 출처 iframe이라 던짐). 실제 Chrome에서 다크·라이트 렌더 확인.
- **재발 방지:** 웹뷰 UI는 **다크 테마에서 먼저** 본다(VS Code 기본이 다크). 네이티브 입력 요소를 줄일 때는 안에 그려지는 부분 전체를 확인한다.

## 39. `Ctrl+Shift+Space`가 macOS에서 앱에 도착하지 않음 (10-15, 1.1.4 개발판)
- **증상:** 체크박스 토글 키 `Ctrl+Shift+Space`를 Mac의 VS Code·Cursor에서 눌러도 아무 일도 없음. "바로 가기 키 문제 해결" 로그에는 Ctrl·Shift 키다운만 있고 **Space 이벤트가 없음** — OS 단계에서 삼켜짐(이 Mac은 입력 소스 전환이 `Ctrl+Space`).
- **왜 못 잡았나:** 키 선택은 VS Code·Cursor의 **기본 키바인딩 목록**만 보고 했고, 동작 확인은 브라우저판 VS Code에 **합성 키 이벤트**를 넣어 했다 — 둘 다 OS/입력기 단계를 지나지 않는다.
- **해결:** `Ctrl+Shift+/`로 변경 → 실제 키보드로 동작 확인. 다만 `/`가 오른쪽 끝이라 두 손이 필요해 **`Ctrl+Shift+Q`**(왼손 한 손, Mac은 빠른 열기 창 안에서만 쓰이는 키, Windows/Linux 비어 있음)로 다시 변경.
- **재발 방지:** 새 키바인딩은 **실제 키보드로, 한글 입력 상태 포함** 눌러 본다(사용자 또는 데스크톱 조작). 합성 이벤트 검증은 "에디터 안"만 증명한다. Space·Enter·방향키처럼 OS·입력기가 특별히 다루는 키는 조합 키로 피한다.

## 40. 렌더 보기에서 연달아 태스크 넣기가 두 번째에서 끊김 (10-18, 개발 중 발견)
- **증상(실제 VS Code에서 확인):** 줄 선택 → `Enter` → 입력 → `Enter`로 첫 태스크는 들어가는데, 다음 입력칸이 열리지 않아 이어서 친 글이 사라짐.
- **원인 두 가지:** (1) 호스트의 "몇 번째 줄에 넣었다"는 응답과 다시 그린 노트가 **어느 순서로든** 올 수 있는데, 응답이 먼저 오면 옛 화면의 같은 줄 번호 아래에 입력칸을 열었다가 다시 그리기가 지움(jsdom 단위 테스트에서 잡음). (2) 삽입 뒤 노트가 **두 번** 다시 그려지는데(편집, 저장), 포커스된 입력칸을 `innerHTML`로 지울 때 Chrome이 그 입력칸의 `blur`를 아직 붙어 있는 상태로 보내 "빈 칸에서 나감 = 닫기" 규칙이 칸을 닫음 — jsdom은 이 blur를 보내지 않아 단위 테스트가 통과했고, **실제 브라우저 VS Code에서만** 드러남.
- **해결:** 다음 칸은 응답과 다시 그리기가 둘 다 온 뒤 연다. 열린 입력칸은 다시 그리기를 넘어 그 줄 아래에 값과 함께 다시 만든다. 다시 그리는 동안의 blur는 무시. 테스트에 실제 Chrome처럼 blur를 보내는 경우를 넣고, **고치기 전 코드에서 실패하는 것 확인**.
- **재발 방지:** 웹뷰의 포커스·입력 흐름은 브라우저 VS Code(`code serve-web` + 헤드리스 Chrome)에서 실제로 쳐 본다. 테스트는 "고치기 전에 실패"를 확인한 다음 믿는다(처음 쓴 테스트는 값을 미리 채워 이 경우를 비껴갔다).

## 41. 체크박스 줄에서 Enter 뒤 Tab 들여쓰기가 안 됨 — Markdown All in One과 충돌 (10-18, 1.0.0~1.1.4)
- **증상(사용자):** 소스 편집기에서 체크박스 줄 끝 Enter → 다음 줄에 `- [ ] `가 생기고 Tab으로 들여쓰던 동작(Markdown All in One)이 이 확장을 깔면 안 됨.
- **원인:** 우리 자동완성은 공백이 쳐질 때 뜨고 최소 글자 수 기본값이 0이라, Markdown All in One이 넣은 `- [ ] `의 끝 공백에도 제안 창(📅 마감일 등)이 떴다. Markdown All in One의 Tab·Enter 키는 `!suggestWidgetVisible` 조건이라 제안 창이 떠 있으면 양보한다.
- **해결(1.1.5):** 체크박스 뒤가 비어 있으면(`- [ ] `) 저절로 띄우지 않는다. 글자를 쓰거나 `Ctrl+Space`로는 그대로. 통합 테스트(빈 줄·들여쓴 빈 줄에서 없음, 글 뒤·Invoke에서 있음) — 고치기 전에 실패 확인. 브라우저 VS Code에서 `- [ ] ` 입력 시 제안 창이 안 뜨는 것 확인(그 환경에서는 Markdown All in One의 목록 이어 쓰기 자체가 동작하지 않아 Enter→Tab 전체는 사용자 확인).
- **재발 방지:** 자동으로 뜨는 UI(제안 창, 호버)는 다른 확장의 키를 막을 수 있다. 널리 쓰이는 Markdown All in One과 함께 기본 흐름(Enter로 목록 잇기, Tab 들여쓰기)을 점검표에 넣는다.

## 42. 자동완성을 "두 글자부터"로 바꿨더니 데스크톱에서 아예 안 뜸 (10-18, 1.1.5 개발판)

- **증상(사용자):** M29에서 `autoSuggest.minMatch` 기본을 2로 하고 영문 글자를 트리거 문자로 넣었다. 데스크톱 VS Code에서 `- [ ] 우유사기 asdfasdf du`까지 쳐도 목록이 안 뜸.
- **원인:** 글자 트리거로 목록이 다시 열리는지는 브라우저 VS Code(하네스)에서 확인할 수 없었고(그 환경은 트리거 문자 자동 제안이 원래 안 열림), 데스크톱 확인 전에 기본값을 바꿨다. 데스크톱에서 왜 글자로는 안 열리는지는 확인하지 않음(되돌렸으므로).
- **해결(1.1.5):** 사용자가 "원래처럼 바로 뜨는 게 더 좋다"고 해서 되돌림 — 기본 0, 공백 트리거. #41의 빈 `- [ ] ` 줄 제외는 유지.
- **재발 방지:** 하네스에서 확인할 수 없는 입력 동작(자동 제안, OS 키)을 바꿀 때는 기본값을 바꾸기 전에 데스크톱에서 먼저 확인한다. 확인 못 한 채 넘길 때는 그 사실을 계획에 적고 사용자 확인 항목으로 둔다(이번에는 그렇게 해서 배포 전에 잡음).
